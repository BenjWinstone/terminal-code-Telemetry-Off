tode — release pipeline

One tarball holds tode and its own copy of terminal-browser. The user needs no Node and no second install. GitHub Actions builds it, Cloudflare R2 holds it, and a Worker serves tode.sh/install.

measured · Electron Helper sets LSUIElement measured · helper runs node v24.18.0 130 MB per download blocker · tode.sh is on Vercel nameservers

00Shape

What happens when a user runs the install line
  1. curl -fsSL https://tode.sh/install | bash hits the Cloudflare Worker.
  2. The Worker reads stable/latest.json from R2 and returns the installer for that exact version.
  3. The installer downloads one tarball, checks its SHA-256, and unpacks it to ~/.local/lib/tode.
  4. The installer writes a shim to $XDG_BIN_HOME/tode.
  5. The shim runs the tode CLI with the vendored Electron binary in node mode.

This copies the terminal-browser pipeline. That pipeline works today, so tode reuses its shape instead of inventing one.

Decide

A 130 MB download is large for a CLI. It is the cost of shipping a browser. terminal-browser already asks users for the same download, so the number is not new. If a user has terminal-browser installed at the pinned version, the installer can clone that tree instead. release.ts already does this with cp -Rc, which is nearly free on APFS.

02Vendoring terminal-browser

Move the download from first run to build time

Today resolveRuntime() tries three sources in order: an env override, a copy already unpacked under RUNTIME_DIR, a clone of the user's own terminal-browser install, then a download from terminal-browser.sh. The download makes the first run slow and needs the network.

Add one source in front of the others: vendored.

// src/runtime/release.ts
const VENDORED = path.join(INSTALL_ROOT, "runtime", "terminal-browser");
// INSTALL_ROOT = dirname(dirname(__dirname)) — the tree this file was unpacked into

export async function resolveRuntime(options = {}) {
  const override = process.env.TODE_TERMINAL_BROWSER_BIN;
  if (override) …                       // unchanged

  if (usable(VENDORED, PINNED_VERSION))  // new, and the normal path
    return { bin: writeLauncher(VENDORED), root: VENDORED,
             version: PINNED_VERSION, source: "vendored" };

  …                                      // pinned / cloned / downloaded stay
}

Keep the other sources. A developer running from a git checkout has no vendored copy, so the download path is still the one that serves them. The source field already reports which path ran, and tode runtime already prints it.

How CI gets the copy

The build job reads PINNED_VERSION from the source, asks terminal-browser.sh/install/v/<version> for that build's URL and hash, downloads it, checks the hash, and unpacks it into the staging tree. The pin is one constant in one file, so an upgrade of the browser is a one-line change plus a release.

03Electron as node

The bundle already contains a node runtime

The Electron binary runs as plain node when ELECTRON_RUN_AS_NODE=1 is set. tode can execute its own CLI with it, so the machine does not need Node installed.

Measured on this machine

Both the main binary and Electron Helper report node v24.18.0 and electron 43.1.1 under ELECTRON_RUN_AS_NODE=1. Node 24 is newer than the Node 22 the project targets, so nothing in dist/ needs a downgrade. 

# bin/tode — what the installer copies to $XDG_BIN_HOME/tode
#!/bin/sh
ROOT="${TODE_INSTALL_ROOT:-$HOME/.local/lib/tode}"
HELPER="$ROOT/runtime/terminal-browser/electron/terminal-browser.app/Contents\
/Frameworks/Electron Helper.app/Contents/MacOS/Electron Helper"
export ELECTRON_RUN_AS_NODE=1
exec "$HELPER" "$ROOT/cli/dist/main.js" "$@"

This removes the last reason tode needs a system Node. It also pins the node version to the one the browser ships, so a user's Node upgrade cannot break tode.

04Keeping the Dock quiet

Use the helper binary, not the main app binary

macOS shows an icon in the Dock for a process that LaunchServices treats as a foreground application. An Electron app is one of those unless its Info.plist says otherwise.

BinaryLSUIElementResult
terminal-browser.app/Contents/MacOS/terminal-browserabsentMay show in the Dock if anything starts the GUI layer.
…/Frameworks/Electron Helper.app/…/Electron HelpertrueNever shows in the Dock, by declaration.

What the test showed

I ran both binaries with ELECTRON_RUN_AS_NODE=1 and asked LaunchServices for each PID. Neither one registered. So the env var alone was enough in this test, and the Dock stayed clean for both.

Use the helper anyway. Its LSUIElement is a guarantee that does not depend on an env var surviving every code path. The cost is one longer path in the shim.

Two more rules

  • Never start the runtime with open -a. That asks LaunchServices for a foreground launch and always produces a Dock icon.
  • Keep ELECTRON_RUN_AS_NODE=1 exported before the exec, not passed as an argument. The current writeLauncher() already does this.

05XDG layout

Most of this is already correct

src/runtime/paths.ts already reads XDG_DATA_HOME, XDG_STATE_HOME and XDG_CACHE_HOME, and falls back to the standard defaults. It also gives terminal-browser its own XDG homes underneath tode's, which stops the two installs from sharing a daemon socket.

PathHoldsState
~/.local/lib/todeThe unpacked releaseNew. The installer writes it. Program only, no user data.
$XDG_BIN_HOME/todeThe shimNew. Default ~/.local/bin.
$XDG_DATA_HOME/tode/vscode profile, db, browser dataDone
$XDG_STATE_HOME/tode/logs, browser stateDone
$XDG_CACHE_HOME/tode/browser cacheDone
$XDG_CONFIG_HOME/tode/user configNew, if tode ever takes one
TODE_INSTALL_ROOToverrides the install rootNew. For tests and for a second install.
$XDG_STATE_HOME/tode/install.jsonversion, channel, install timeNew. upgrade reads it.

Why the program is not under share/

~/.local/share/tode/ already holds live user data: the vscode profile, the browser profile, the cached palette and the database. The upgrade swaps the whole tree by rename, so the program must sit somewhere that holds nothing the user owns. Otherwise each upgrade would delete the imported settings.

~/.local/lib mirrors /usr/local/lib and pairs with the ~/.local/bin shim, so a program payload belongs there. app/ is not an XDG convention; it is terminal-browser's own choice. tode does not copy it.

One trade-off: there is no XDG_LIB_HOME. If a user moves XDG_DATA_HOME, the program stays at ~/.local/lib/tode while the data follows. That is correct, because a program payload is not XDG data, but it does mean two roots. TODE_INSTALL_ROOT exists for anyone who needs to move it.

RUNTIME_DIR at $XDG_DATA_HOME/tode/runtime stays as it is. It holds browser copies that a git checkout downloads. A normal install uses the vendored copy and never writes there.

06The upgrade command

tode upgrade
tode upgrade            install the latest build on this channel
tode upgrade --check    report what is available, change nothing
tode upgrade --version <v>   move to one exact build

Steps, in order:

  1. Read VERSION and CHANNEL from the install root.
  2. Refuse if the install is a dev shim. Tell the user to run git pull instead.
  3. GET tode.sh/install/latest.json, or /install/dev/latest.json for the dev channel.
  4. Stop if the versions match. Print one line and exit 0.
  5. Download the tarball. Check the SHA-256 from the manifest. Delete the file if the hash is wrong.
  6. Unpack to ~/.local/lib/tode.new, then rename over tode. A rename is atomic, so a failed download never leaves a half install.
  7. Rewrite the shim, because the paths inside it carry the version.
  8. Run tode shutdown first, so the old code-server does not keep running against the new tree.

Reuse download() and unpack() from release.ts. They already stream, hash and stage correctly.

07GitHub Action

The same five jobs as terminal-graphics-engine
JobDoes
prepareDecides channel and version. A tag v* or a manual bump gives stable. A push to main gives dev as main-<sha>. Any other branch gives a pinned build that does not move the channel.
buildRuns tsc, fetches the pinned terminal-browser for the target, stages the tree, writes VERSION and CHANNEL, makes the tarball, and writes manifest-<target>.json with the size and hash.
workerwrangler deploy for the release Worker.
releaseMerges the per-target manifests, uploads to R2, and flips latest.json last.
github releaseFor stable only. Creates the tag's release and attaches the tarballs.

The latest.json flip must be the last write. Then a failed upload never points users at a version whose tarball is missing.

Targets

Start with darwin-arm64 only. The site already says Linux is coming. tode reads the terminal colour over OSC and installs a font into ~/Library/Fonts, so Linux needs work beyond the pipeline.

Runner

The build only runs tsc and tar, so ubuntu-latest can build the darwin tarball. The terminal-browser tarball is fetched, not compiled. No macOS runner is needed, and no code signing is needed while the app comes from the terminal-browser release.

08Cloudflare

R2 for the bytes, a Worker for the routes

Blocker — do this first

tode.sh answers with ns1.vercel-dns.com and ns2.vercel-dns.com today. A Worker route needs the zone to live on Cloudflare, so the nameservers must move. terminal-browser.sh already did this: Vercel lists it as registrar with Third Party nameservers.

The website keeps working through the move. Cloudflare imports the existing records, and Vercel keeps serving the site through them. Plan for up to a few hours of propagation, and do the move before the first release.

Steps in the dashboard

  1. Sign in at dash.cloudflare.com with rob@zenbu.dev through Google.
  2. Add a site → tode.sh → Free plan. Let Cloudflare scan the DNS.
  3. Check the imported records against Vercel's. Keep the apex and www pointing at Vercel.
  4. Copy the two Cloudflare nameservers.
  5. In Vercel, open the tode.sh domain and set those nameservers at the registrar.
  6. Wait for Cloudflare to report the zone as active. Confirm https://tode.sh still serves the site.
  7. R2 → create bucket tode-releases. Same region as the account default.
  8. Workers → the Worker is deployed by CI, not by hand. Nothing to create here.
  9. My Profile → API Tokens → create the token below. Copy it once.
  10. Add the token to the GitHub repo as CLOUDFLARE_API_TOKEN, and the account id as CLOUDFLARE_ACCOUNT_ID.

09The install script

tode.sh/install

scripts/install.sh ships in the repo with three placeholders. The publish step fills them in and uploads one copy per version, so a pinned URL always serves the installer that shipped with that build. 

VERSION="__VERSION__"
CHANNEL="__CHANNEL__"
PLATFORMS="__PLATFORMS__"     # target  sha256  size  file

What it does:

  1. Reads uname -s and uname -m, and stops with a clear message on an unsupported pair.
  2. Downloads the tarball for that target with curl --retry 3.
  3. Checks the SHA-256 with shasum -a 256 -c.
  4. Unpacks to ~/.local/lib/tode.new, then renames over ~/.local/lib/tode.
  5. Writes the shim to $XDG_BIN_HOME/tode and marks it executable.
  6. Writes install.json to $XDG_STATE_HOME/tode.
  7. Prints how to add ~/.local/bin to PATH if it is missing.

Reuse the clone trick

If ~/.local/share/terminal-browser/app already holds the pinned version, the installer can cp -Rc it instead of downloading 130 MB. On APFS this clones blocks and costs almost no disk. release.ts has the code; the installer needs a shell version.

11Risks

What can go wrong, and the answer
RiskAnswer
The nameserver move breaks the site.Import the records first and compare them against Vercel before switching. Keep the Vercel project untouched. The move is reversible.
130 MB per install.Clone an existing terminal-browser install when the version matches. Otherwise accept it; the product is a browser.
R2 single-request limit.Wrangler uploads in one request and the API caps it near 315 MB. The tarball is 130 MB, so there is room. The publish script should still check the size and fail with a clear message.
The vendored browser goes stale.PINNED_VERSION is one constant. Add a CI check that the pinned version still resolves, so a deleted release fails the build and not the user.
Gatekeeper blocks the app.The app comes from the signed terminal-browser release, and curl | bash sets no quarantine flag. Verify on a second machine before the stable tag.
An upgrade runs while tode is open.upgrade calls shutdown first, and swaps by rename. A running process keeps its open files until it exits.
Node 24 differs from Node 22.The helper reports v24.18.0. Add --target es2022 parity in CI by running the tests with the vendored binary, not with the system Node.
